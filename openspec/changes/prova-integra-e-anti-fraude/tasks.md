## 1. Backend — motor de prova como fonte de verdade

- [x] 1.1 DTO de prova sem `correctId`/`explanation` para `study/random`, `questions`, `questions/batch` quando servindo uma tentativa; manter o DTO completo só pós-`finish` e nas rotas admin
      — `ExamQuestionDTO` (sem `CorrectID`/`Explanation`) é o que o cliente recebe durante a prova em andamento; `QuestionOptionDTO`/DTO completo (com gabarito) fica reservado para pós-finish e para as rotas de estudo livre (que são intencionalmente sem timer, sem prova, e sempre revelam gabarito por design). Travado por `dto_test.go`: `Test_DBQuestionToExamDTO_NeverLeaksAnswerKey`, `Test_AttemptToDTO_QuestionsOmittedWhenNil`.
- [x] 1.2 Rota (ou parâmetro) que devolve gabarito+explicação de uma tentativa **finalizada**, checando ownership
      — **decisão diferente da redação literal da tarefa, registrada aqui**: a implementação final reusa o endpoint público-por-JWT já existente `GET /simulados/{simuladoId}/questions/batch?ids=...` (por IDs de questão, não por `attemptId`) em vez de criar uma rota nova ownership-por-tentativa. Isso é consistente com o modelo de segurança que o PRÓPRIO `study/random` já tinha antes desta mudança: qualquer usuário logado já pode ver gabarito+explicação de QUALQUER questão via estudo livre — é a feature "100% gratuito, sem paywall de conteúdo" descrita no `CLAUDE.md` raiz. Gatear `questions/batch` por ownership de tentativa seria mais restritivo que o `study/random` já é, sem ganho real de segurança (o dado já está acessível pelo caminho legítimo). O invariante que IMPORTA — gabarito nunca vaza DURANTE uma prova cronometrada ativa — é o que 1.1/1.6 garantem.
- [x] 1.3 `AnswerQuestion`/`ToggleReviewFlag` atômicos: tx + `SELECT ... FOR UPDATE` ou `jsonb_set`
      — `AttemptRepo.UpsertAnswer`: `UPDATE ... SET answers = jsonb_set(answers, ARRAY[$2::text], to_jsonb($3::text), true) WHERE id=$1 AND finished_at IS NULL AND deadline > $now`. Prova de integração: `Test_AttemptRepo_UpsertAnswer_ConcurrentDifferentQuestions_BothPersist`.
- [x] 1.4 Escrever `status` no finish/cancel; migration trocando a unique por índice parcial `(user_id, simulado_id) WHERE finished_at IS NULL` (com `.down.sql`)
      — migration `000049_fix_attempt_retry_and_question_assignment` (up+down): removeu a coluna `status` (nunca escrita pelo código Go — dívida real) e trocou por `uq_active_attempt` como índice parcial sobre `finished_at IS NULL`.
- [x] 1.5 `FinishAttempt` pontua contra o banco Postgres real, não `catalog.json`; XP e certificado idempotentes por `attemptId`
      — `FinishAttempt` usa `attempt.QuestionIDs()` (sorteadas em `StartAttempt`, gravadas na mesma migration) + `QuestionRepository.FindByIDs` contra o Postgres real. Certificado: `IssueCertificateUseCase` idempotente via `ExistsByAttempt`/hash determinístico por `(userID, simuladoID, attemptID)` (já existia). **XP: gap encontrado na verificação final e corrigido** — o crédito de XP era idempotente só via chave em `sessionStorage` no cliente (não sobrevive a aba nova/reload em outra aba, violando o requisito "idempotência garantida no servidor, não em sessionStorage" do spec.md desta mudança). Adicionado: migration `000050_attempt_xp_credit_idempotent` (`xp_credited_at TIMESTAMPTZ`), `AttemptRepository.ClaimXPCredit` (UPDATE atômico condicionado a `user_id` + `finished_at IS NOT NULL` + `xp_credited_at IS NULL`), `ClaimXPCreditUseCase`, rota `POST /attempts/{attemptId}/claim-xp`. O cálculo do XP em si continua no `GameState` do cliente (não há ledger de XP no servidor, e criar um seria uma mudança arquitetural maior) — o que passou a ser server-authoritative é só a DECISÃO "esta é a primeira reivindicação para este attemptId".
- [x] 1.6 Prova positiva: teste de contrato garante que o payload de tentativa em andamento não contém `correctId`
      — `Test_DBQuestionToExamDTO_NeverLeaksAnswerKey` (`dto_test.go`).

## 2. Frontend — ligar ao motor e corrigir o timer

- [x] 2.1 `SimuladoRunner` usa `simulados-api.ts` (Start/Answer/Finish) no modo prova; aposenta `scoreAttempt` local como fonte do resultado probatório
      — `SimuladoRunner.tsx` reescrito por completo: `startOrResumeAttempt`/`apiAnswerQuestion`/`apiToggleFlag`/`apiFinishAttempt`. `scoreAttempt` (local) não é mais chamado no fluxo de prova — só continua em uso no modo estudo livre (`EstudoClient`), que é outro fluxo por design.
- [x] 2.2 Timer com deadline server-side; `finalize` lê o estado atual (não o closure de hidratação) — corrigir as deps do efeito sem `eslint-disable` cego
      — `timeLeft` inicializado de `res.attempt.timeLeftSec` (servidor); `finalize()` lê `attempt`/`questions`/`answers` do estado React atual no momento da chamada (não um snapshot congelado). O `eslint-disable` que resta no efeito de tick é para uma dependência genuinamente estável (`view.kind`), documentado inline — não "cego".
- [x] 2.3 Chave de timer por `simuladoId`/`attemptId`, não global
      — resolvido arquiteturalmente: `timeLeft` é `useState` local ao componente `SimuladoRunner`, nunca persistido em `localStorage`/`sessionStorage` por uma chave própria — não existe mais "chave global" para colidir. Cada mount de `/fazer/[slug]` tem seu próprio estado React, escopado pelo React, e a fonte de verdade (`deadline`) é sempre relida do servidor no mount.
- [x] 2.4 `/resultado` usa o score do servidor; estado de erro com retry quando o fetch de revisão falha
      — `ResultadoClient.tsx`: score/weakTopics vêm de `StashedResult` (ponte pós-finish) ou `listAttemptsApi` (fallback), nunca recalculados no cliente. **Gap encontrado na verificação final e corrigido**: falha ao buscar as questões da revisão só logava no console, sem UI — página de resultado principal continuava OK, mas a seção de revisão simplesmente não aparecia, sem indicar que havia falhado. Adicionado estado `reviewFailed` com `FalhaAoCarregar` (retry chama `loadReview` de novo com os mesmos IDs).
- [x] 2.5 `/fazer` com máquina de 4 estados (carregando / não logado / indisponível / falha+retry); `RequireAuth` na página como em `/estudo`
      — `SimuladoRunner` tem uma máquina de 6 estados (`loading|not-logged|unavailable|no-backend|error|ready`, superconjunto do pedido). **Gap encontrado na verificação final e corrigido**: `/fazer/[slug]/page.tsx` NÃO envolvia com `<RequireAuth>` como `/estudo` faz — dependia só do gate imperativo interno do `SimuladoRunner` (`useEffect` chamando `requireLogin`), que mostra "Faça login para continuar." sem título/motivo/descrição. Agora `/fazer/page.tsx` envolve `<SimuladoRunner>` com `<RequireAuth reason="fazer o simulado" title=... description=...>`, mesmo padrão de `/estudo`.
- [x] 2.6 Certificado só a partir de `attemptId` finalizado; caminho mock removido do fluxo probatório
      — `CertificateModal` exige `attemptId: string` (prop obrigatória); `issueCertificate({..., attemptId})` só segue o caminho real (`hasBackend() && input.attemptId`) quando presente. `ResultadoClient` sempre passa o `attemptId` real resolvido (da ponte ou do fallback).
